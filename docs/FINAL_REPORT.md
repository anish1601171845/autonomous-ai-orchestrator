# Final Project Report: Autonomous AI Multi-Agent Workflow Orchestrator

## 1. Problem statement

Design a self-governing multi-agent system that uses NLP and LLM orchestration to scope, plan, negotiate and
execute complex enterprise tasks automatically, adapting to dependencies and workloads.

## 2. Solution summary

A LangGraph state machine coordinates eight specialised agents:

1. **Scoping:** turns a requirement into structured tasks with complexity, urgency, impact and acceptance criteria (LLM or rule-based).
2. **Classification:** a GridSearchCV-tuned model assigns development / testing / documentation / deployment / analysis.
3. **Planning:** semantic candidates plus a GraphSAGE GNN predict directed dependencies, and cycle-safe insertion yields a valid DAG.
4. **Priority:** an ML model predicts low / medium / high / critical from text, urgency, complexity, impact and dependency fan-out.
5. **Workload:** capability-aware allocation via a PPO policy or the least-loaded heuristic, whichever evaluates better.
6. **Coding:** generates modules and unit tests (or docs, CI and Dockerfile) into an isolated workspace.
7. **QA:** AST security scan, ruff, then pytest in a resource-limited sandbox; failures go back to Coding with feedback, with bounded retries.
8. **GitHub:** repository insight, reviewer recommendation from commit file ownership, and approval-gated branch + PR.

Everything is persisted (SQLAlchemy), exposed through FastAPI, and visualised in Streamlit.

**End-to-end run** (`reports/sample_run/`): the example student-management requirement produced 11 tasks
(5 development, 4 testing, 1 analysis, 1 documentation), a valid DAG predicted by the GNN, assignments across
5 agents, and generated modules for configuration, database, registration, login and dashboard. All 37
generated tests passed in the sandbox, and the workflow stopped at `awaiting_approval`.

### Findings

- **Similarity is not dependency.** Cosine similarity reached ROC-AUC 0.71 but average precision only 0.14, because
  sibling tasks ("test login" and "test billing") look alike but are independent. Learning direction needs the GNN.
- **Simple beats complex for text classification.** Logistic regression matched or beat tree ensembles at a fraction of the fit time.
- **Priority is the hardest task** (macro-F1 0.76). Labels are a noisy function of urgency, impact, complexity and fan-out,
  as real triage is, and adjacent classes (medium/high) cause most of the confusion.
- **RL is not automatically better.** PPO learned a more balanced and slightly more reliable policy but did not
  reduce makespan below a strong heuristic. The system therefore selects least-loaded automatically. This is an honest
  outcome and the motivation for the reward-shaping and action-masking future work below.
- **Distribution shift was visible and fixed.** The first GNN produced missing prerequisites for requirements without
  a database. Adding that structural variety to the synthetic generator fixed the predicted plans for unseen
  e-commerce and HR requirements.

## 4b. Real-data extension

Two real labelled datasets were integrated (week 1: "collect enterprise datasets"):

- **PROMISE NFR requirements** (623 statements, 12 labels). They power the scoping agent's *requirements-document mode*. The test file comes
  from different projects: functional-vs-NFR accuracy is 0.786 against a 0.36 baseline. The 12-type accuracy
  is 0.700 against 0.64, with macro-F1 0.570. Cross-validation on the training projects is higher
  (about 0.91 for F vs NFR), showing that wording is project-specific. The weakest case is security requirements phrased as
  permissions ("only users with X access…").
- **Multilingual support tickets** (4,000 tickets; en/de/es/fr/pt). They power the new ticket intake agent. Hold-out accuracy is type 0.646,
  priority 0.626 and queue 0.569, against baselines of 0.40, 0.41 and 0.33, and is consistent across languages.
  An ablation showed that the business-type field biased predictions and that the long-e-mail corpus hurt one-line tickets.
  Removing the field and adding subject-only training copies raised short-ticket priority accuracy from 0.531 to 0.625.

End-to-end runs: the 70-statement PROMISE test file submitted as one document produced 26 tasks (8 feature groups plus
security, integration, performance, UI and compliance tasks), all completed with 85 generated tests passing. A German
payment-failure ticket was triaged as Incident / high and executed as a 5-task workflow.

## 6. Limitations and threats to validity

- Synthetic labels and graphs come from rules the models can learn. Scores are upper bounds for this pipeline, not field performance.
- The RL simulator's duration and failure model is hand-designed. Policies may not transfer to real teams without calibration.
- Template code generation is generic. Domain logic needs an LLM backend or human edits.
- Process-level sandboxing is not a security boundary against a determined attacker. Use container isolation in production.

## 7. Future work

1. Label 1–2k real issues from public repositories, and add LLM-assisted weak labelling with human review.
2. Retrain the GNN with transformer embeddings and evaluate on real dependency links ("blocked by" issue references).
3. Use maskable PPO (sb3-contrib) with makespan-aware reward shaping, and train on workloads calibrated from commit history.
4. Use a Postgres-backed LangGraph checkpointer so crashed workflows resume, not fail.
5. Add container-based sandbox execution and authentication/RBAC on the API.
